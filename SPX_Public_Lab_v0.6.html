What is SPX?

Super Positioned Text [SPX] is an experimental live encoding and detangling system. Source characters are mapped into Node-derived shape/topology groups, on/off sets, and locator values. Those values form related rails and a heatmap/grid view; SPX then records reversible relationships between states, adds live parity/programming state, and assembles the result into a structured DataGraph.

The DataGraph is then reduced into the final SPX PATH: simple runs are handled first, the Reflection Wheel and generated SPX token arrays replace known structures, graph separators are consumed by the deterministic grammar, and SPX-QEC may reference repeated objects that remain in the live path. Detangle performs those stages in reverse to recover the source.

Super Positioned Text [SPX]

Public Working Whitepaper - 2026 Edition

Creator and original designer: 3Douglas Pihl (@Z0M8I3D, DigiMancer3D)
Status: Experimental, untested research concept

A note from 3D: Super Positioned Text [SPX] is an untested concept for live encoding data using similarly untested methods. Please use it responsibly, and please enjoy your day. —3D

Abstract

SPX is an experimental deterministic encoding and reconstruction system designed around live transformation. Input symbols are mapped into Node-derived structural descriptions, separated into related data rails, transformed into reversible relationships between neighboring states, combined with parity/programming information, and assembled into a structured intermediate called a DataGraph. The DataGraph can then be reduced into an SPX PATH using the Reflection Wheel, predefined SPX token families, structural grammar, and later SPX-QEC live references.

The project explores a “between two states” model: a later state can be represented partly by its relationship to the state before it. This is a classical deterministic process. SPX sometimes uses faux-quantum or super positioned language because multiple codependent views are flattened and later detangled; SPX is not literal quantum computation or quantum entanglement.

1. Node structure

Each supported character has a Node-derived structural description with a group (shape/topology family), a set (the on/off member within that family), and a locator used by the heatmap/grid mapping. Similar sets may appear across different groups. A decoding identity, however, must remain distinguishable. Historical SPX manually adjusted locator values when collisions were discovered; the repaired research model audits those identities while preserving the Node structure.

2. Heatmap, grid, and rails

Node information is mapped into predictable heatmap/grid positions and related data rails. The rails are cooperating views of one source object, not separate messages. Their order, lengths, relationships, parity, and locator tape constrain detangling.

3. Between-state transformation

SPX carries an initial state and records how later states relate to what came before. In binary, the historical relation can be expressed as same → 1 and different → 0 after the first value is carried. The repaired lab formalizes the reversible form as CFTT. The transform exposes relationships for later tokenization; it is not, by itself, compression.

4. Live parity and history

The historical parity experiment uses an approximately 18-position working state. The first loop accepts 18 fresh positions; later loops can carry the prior end-parity in slot 1 and accept 17 fresh positions. This lets the state machine continue with a loop count and carry without keeping the entire previous payload in active memory. The carried parity does not, by itself, reconstruct discarded history.

5. DataGraph

Mapping, relations, parity, programming data, rails, and locator/index information are assembled into an ordered DataGraph. Because encoder and detangler share the grammar, compact output does not need to label every section. The DataGraph is the inspectable intermediate; it is not necessarily the smallest SPX representation.

6. Reflection Wheel and SPX tokens

The canonical uppercase Reflection Wheel uses A=1 … Z=26. A contiguous range can be described by its endpoints, such as AZ, and the canonical default is shared codec knowledge. Simple homogeneous binary runs are handled first using the reserved Reflection Wheel state identifiers: 000000 → AF and 11111 → aE. A identifies a repeating 0-state and a identifies a repeating 1-state; the following uppercase reference character carries the run length. Generated pattern families, heatmap/index values, and known graph structures are then reduced through deterministic SPX token rules.

7. SPX-QEC live references

QEC is a later, distinct layer. It searches the already-reduced current path for reusable structures. The first occurrence remains as reconstruction material; later occurrences can become compact live references. The historical Hello World paper fixture remains a compatibility example: L102 DataGraph → L77 static SPX → L73 QEC SPX PATH.

8. Detangling

Detangling reverses the process in a bounded order: QEC references, SPX token/structure grammar, DataGraph recovery, relation inversion, and Node/grid reconstruction. The public build reports unresolved historical material rather than guessing when a proven inverse is unavailable.

9. Live operation and embedded research

SPX was conceived as a live demonstration, so the encoded state changes as a user types. The deterministic state-machine design also suggests an embedded implementation: ROM/Flash for fixed tables, a small working parity buffer and carry state, and a bounded history window for QEC. An STM32-class microcontroller is a practical first target for that research.

10. Verification research

SPX historically explored multiple independent checking views, including parity families, Node/group restrictions, geometry-inspired witnesses, and dual-plane/polygon comparisons. These remain experimental. Debugging information, tests, hashes, and verbose audit metadata are deliberately kept separate from the compact SPX PATH whenever possible.

11. SPX Boot Camp

The public Boot Camp page is a compatibility exercise for a pasted SPX output. It classifies the object, attempts a proven detangle, rebuilds recovered source text with the current encoder, checks deterministic reproduction and round-trip behavior, and reports token activity. An unresolved result can mean the current build does not yet implement the historical rule that created the object.

12. Limits and responsible claims

SPX is experimental. It is not established cryptography, a standardized error-correcting code, or a guarantee that arbitrary data will compress. A short-looking path is not automatically net compression: shared LUTs and deterministic rules are codec knowledge available to both sides, and arbitrary high-entropy data cannot always be shortened losslessly in a self-contained representation.
